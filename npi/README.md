# NPI-чек-лист

Инструмент для технолога SMT и THT: последовательный чек-лист вывода нового
изделия в производство, регистр находок с фото-доказательствами и
профессионально оформленный отчёт.

Всё считается в браузере. Никаких учётных записей, облаков и сборов
телеметрии. Языковая модель подключается по желанию и работает локально.

---

## Запуск

```
node serve.js
```

Откройте адрес, который напечатает команда (по умолчанию
`http://127.0.0.1:8790/`).

Можно и без сервера: откройте `index.html` прямо из папки. Чек-лист,
находки, фото и отчёт работают полностью. Не работает только модель — ей
нужен локальный адрес, с которого файл не может обращаться.

---

## Как работать

1. **Создайте изделие** и заполните реквизиты: обозначение, ревизию,
   класс IPC, сплав, линию. Они попадут в отчёт.
2. **Пройдите гейты по порядку.** На каждом шаге нажмите «Соответствует»,
   «Риск» или «Не применимо» — повторное нажатие снимает ответ. Рядом с
   шагом указано, чем проверять, какую норму применять и что считается
   доказательством.
3. **Нашли проблему — заведите находку.** Опишите, что наблюдаете, прикрепите
   фотографии, назначьте владельца и срок. Находка живёт отдельно от шага:
   её можно закрыть, не отвечая на шаг заново.
4. **Соберите отчёт.** Вкладка «Отчёт» показывает документ целиком. Кнопка
   «Печать» сохраняет его в PDF через диалог браузера. Реквизиты и находки
   можно выгрузить в JSON и перенести на другой компьютер.

Статусы шагов означают вот что:

- **Соответствует** — шаг пройден, есть доказательство.
- **Риск** — есть замечание. На шаге уровня B это блокирует выпуск.
- **Не применимо** — шаг не относится к изделию. Гейт закрывается, но риск
  на этом шаге всё равно попадёт в вердикт.
- **Пусто** — шаг не отвечен. Покрытие не растёт, гейт не закрывается.

Уровни находок: **B** — блокирует выпуск, **C** — условный выпуск,
**W** — наблюдение, на вердикт не влияет.

## Гейты

| | Гейт | Что закрывает |
|---|---|---|
| G0 | Входной пакет данных | Состав, ревизии, заказчик, класс, сплав, линия |
| G1 | DFM-разбор | Шаги, зазоры, тепловые поля, веса, реперы |
| G2 | Документация и планирование процесса | Чертежи, управление изменениями, маршрут |
| G3 | Материалы и готовность по MSL | Сертификаты, MSL, сушка, склей, припой, паста |
| G4 | Трафарет и печать | Геометрия, давление, отсос, очистка, отпечаток |
| G5 | Монтаж компонентов | Программа, фидеры, ориентирование, перекос |
| G6 | Профиль оплавления | Разогрев, выдержка, пик, охлаждение, профили |
| G7 | THT: волна и селективная пайка | Формовка, волна, селективная, заполнение |
| G8 | Контроль и испытания | AOI, рентген, ICT, очистка, контроль покрытия |
| G9 | Ремонт и восстановление | Число циклов, термическое воздействие |
| G10 | Раскрой, покрытие, очистка | Ломкость, изгиб/скрутка, чистота остатков |
| G11 | Первая партия и опытный запуск | Пилотный выпуск, замеры, брак, выход годных |
| G12 | Квалификация и выпуск в серию | Критерии, подписанный пакет, передача |
| G13 | Раннее серийное сопровождение | Наблюдение, реагирование, обратная связь |

Гейт открывается, когда закрыт предыдущий применимый гейт.

## Подключение модели

Модель не обязательна. Когда она есть, помогает с черновиками: описать
находку по фото и заметкам, перечислить недостающие доказательства,
сделать краткое резюме для отчёта. **Готовый текст всегда правит человек.**
Модель не выставляет статусы, не назначает уровень и не выносит вердикт.

Настройки — в `llm.config.json`:

```json
{
  "baseUrl": "http://127.0.0.1:11434/v1",
  "model": "qwen3.8-flash-next",
  "apiKey": ""
}
```

`baseUrl` — адрес локального сервера модели, совместимого с интерфейсом
OpenAI. `apiKey` нужен только если сервер его требует; пустая строка
означает «без ключа». Те же значения можно задать переменными окружения
`LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY` — они имеют приоритет.

Проверить связь: вкладка «Настройки» → «Проверить связь». Отдельно
доступен адрес `/api/llm/status` — он показывает адрес, модель и наличие
ключа, **не выдавая сам ключ**.

Модель с кириллицей в ключе не роняет сервер: он отвечает понятной ошибкой
и продолжает работать.

## Файлы

```
index.html            разметка-каркас
assets/data.js        содержание: гейты, шаги, критерии, нормы
assets/npi-core.js    расчёт: покрытие, состояние гейтов, вердикт
assets/report.js      построение отчёта из состояния
assets/store.js       состояние в localStorage, фото в IndexedDB
assets/llm.js         обращение к модели
assets/app.js         интерфейс и маршруты
assets/style.css      оформление
serve.js              раздача файлов + прокси к модели
llm.config.json       настройки модели
scripts/check-data.js проверка содержания чек-листа
scripts/check-report-style.js  проверка оформления отчёта
tests/                автоматические проверки
docs/decisions.md     почему сделано так, а не иначе
```

Содержание правятся в `assets/data.js`. Проверка: `node
scripts/check-data.js`. Она ловит дубликаты, шаги без критерия приёмки,
ссылки на несуществующие нормы и отметки «сверено» без указанной нормы.

## Пример прохода

В каталоге `demo/` лежит полный проход чек-листа на вымышленном изделии —
плата управления ВЧ-модуля, класс IPC 3, SAC305, линия SMT-2. Собрано тем же
кодом, что и интерфейс: `node demo/demo-walk.js`.

```
Изделие:        Плата управления ВЧ-модуля ВЧ-4412
Обозначение:    PCB-4412-B рев. C
Класс IPC:      3, сплав SAC305, линия SMT-2
Ответов:        ok 93, риск 7, не применимо 3 (всего 103)
Покрытие:       100 %
Находок:        5 (открытых 4)
Вердикт:        НЕ ВЫПУСКАЕМ
```

Что показывает пример:

- Все 103 шага отвечены, покрытие 100 %, но вердикт **НЕ ВЫПУСКАЕМ**:
  открыта находка уровня B (недостаточное заполнение отверстий на разъёме).
  Покрытие и вердикт — разные вещи, и это главное, что должен показать
  инструмент.
- Семь гейтов под риском. Гейт g7 не пройден, поэтому g8–g13 заблокированы:
  дальше по цепочке не пускает.
- Пять находок с фото-доказательствами: закрытая B, открытая B, две C разного
  статуса и одна W-наблюдение, которая вердикт не меняет.
- Перенос на другой компьютер проверён в оба конца: документ прошёл `validateImport`,
  импорт вернул все 5 фото, вердикт не изменился.
- Отчёт — 1,7 МБ самостоятельного HTML с пятью фото-плитками, поэтапным
  приложением на все 103 шага, блоком подписей и разделом «о чём этот отчёт
  не говорит».

Файлы:

```
demo/report.html     готовый отчёт (открывается в браузере, печатается в PDF)
demo/WALKTHROUGH.md  журнал прохода: каждый шаг с ответом и доказательством
demo/project.json    экспорт проекта со всем фото внутри
demo/photos/         снимки-доказательства
demo/demo-walk.js    скрипт, который всё это собирает
```

Фотографии сгенерированы как иллюстрации. Изделие, замеры и находки
вымышлены: это демонстрация механики, а не аудит реального производства.

## Проверки

```
node tests/run-all.js
```

Проверяется ядро, построение отчёта, хранилище, сервер с прокси, интерфейс
в целом и — последним набором — оформление отчёта.

Последний набор важен отдельно. Проверка «в разметке есть класс» убеждается
в намерении, а не в результате: правило может быть в таблице стилей и при
этом не применяться. Поэтому check-report-style.js строит отчёт по образцу,
вручную разворачивает var(--…) по :root (jsdom этого не умеет) и спрашивает
у jsdom вычисленные стили 50 элементов. Отдельным файлом:

node scripts/check-report-style.js npi/demo/report.html

Оформление и дымовой тест интерфейса требуют jsdom:

```
npm install --no-save jsdom
```

Без него запустится всё, кроме дымового теста интерфейса, и общий запуск
об этом честно скажет.

## Ограничения

- Данные живут в браузере на том компьютере, где открыт инструмент. Чистка
  браузера их удаляет — делайте выгрузку в JSON.
- Фото во встроенном режиме (когда IndexedDB недоступен) считаются
  рассчитанными на десятки снимков, не на тысячи.
- Инструмент не заменяет стандарты. Он напоминает, чем руководствоваться,
  и фиксирует, что сделано. Текст стандарта нужно читать в самом стандарте.
- В нескольких шагах числовой порог намеренно не указан — см. «не сверено»
  в интерфейсе и раздел T-D10 в `docs/decisions.md`.
