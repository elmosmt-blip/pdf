## Why 8D is used
An 8D report is a structured problem-solving record for internal escapes, customer complaints or repeated process defects.

In SMT and through-hole work it connects the complaint to traceable evidence: product, lot, line, process step, component, paste, stencil, feeder, reflow or wave and selective solder parameters, inspection program and test data.

The report is useful only if another engineer can follow the logic, repeat the verification and see where the conclusions came from.

## D1 team and D2 problem description
D1 names a small working team with authority and knowledge: process engineering, production, quality, materials, equipment maintenance, design, and supplier support where materials or tooling are involved.

D2 describes the problem as observed, not as a conclusion. Include product, line, process step, defect mode, quantity, date, lot, measurement method, customer impact, and whether the defect is an occurrence or a detection escape.

A problem statement that already names the cause has skipped the investigation.

## D3 containment
Containment protects the customer while the root cause is still under investigation.

Typical actions are quarantining suspect lots, sorting outgoing stock, adding inspection, holding shipments, notifying the customer, freezing process changes, and reworking only under a controlled method.

Each action needs an owner, a date and a verification method. Containment is not corrective action: it reduces risk without removing the cause.

## D4 root cause, occurrence and detection
A complete 8D separates the occurrence root cause from the detection escape.

Occurrence may involve paste rheology, stencil aperture design, reflow ramp and soak, component coplanarity, feeder accuracy, placement pressure, wave dwell, selective nozzle condition, flux activity, preheat, cooling or thermal mass. Detection may involve AOI coverage, in-circuit coverage, visual inspection limits or test escape.

Both sides need evidence, and the evidence should be traceable to lot or program records rather than recalled.

## D5 corrective action and D6 validation
Corrective action addresses the proven root cause, not the visible symptom.

Examples: changing stencil aperture geometry, updating the reflow profile inside the paste and component datasheet window, replacing a feeder, adjusting wave or selective solder parameters, updating an AOI program, adding a poka-yoke, or changing supplier control.

Implementation needs an owner and a date, and validation should show the effect on the metric rather than the completion of the task.

## D7 prevention and D8 closure
Prevention updates the management system so the class of problem is less likely to recur: PFMEA, control plan, work instructions, operator training, design rules, incoming inspection, supplier agreements, tooling maintenance, and horizontal deployment to similar products or lines.

Closure is supported by evidence: containment records, root-cause data, validation results, updated documents, and a measured effectiveness check.

## Where 8D reports fail
The usual failures are presenting containment as correction, stating a root cause without data, ignoring the detection escape, missing owners or dates, vague language, missing traceability, and closure without an effectiveness metric.

Another frequent failure is no horizontal deployment, so the same defect returns on a similar product.

A good 8D is auditable: it shows what was found, what was done, who did it, when, and what the data said afterwards.

## Key takeaways
Keep occurrence and detection separate through D4, because one corrective action rarely closes both.
Treat containment as a holding action, since releasing on containment alone leaves the cause in the process.
Close on a measured metric, because a completed action list is not evidence that the defect rate moved.

## Common mistakes
Writing the cause into the D2 problem statement :: Describe what was observed, because a leading statement biases every later step.
Closing on the corrective action date :: Verify the metric afterwards, since implementation and effect are different events.
Skipping horizontal deployment to similar products :: Apply the fix to similar products, because the same design repeats across the line.

## Glossary
Occurrence root cause :: The process condition that created the defect.
Detection escape :: The defect that passed the inspection or test meant to catch it.
Poka-yoke :: A design or process feature that prevents an error from being made.
Horizontal deployment :: Applying a corrective action to other products, lines or sites with the same risk.
