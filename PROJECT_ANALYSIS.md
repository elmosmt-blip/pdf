## 3. Архитектура: как есть и как должно быть

### Текущая схема

```
[Браузер] ──fetch──► /data_full.json  (165 КБ, из public/)
           ──fetch──► /equipment.json ( 99 КБ, из public/)
           ──<img>──► /api/img?url=<любой внешний URL>  ──fetch──► Интернет
                          │
                          └── НЕТ allowlist, НЕТ лимита размера, НЕТ таймаута,
                              content-type отдаётся как есть (SSRF / XSS / DoS)
```

Ключевые архитектурные решения и их цена:

1. **Вся страница — `'use client'`.** SSR/ISR не используются вообще: HTML‑оболочка пустая, контент появляется после hydration + двух fetch. Для «новостного» продукта это означает: поисковики и превью‑линки видят пустую страницу, LCP зависит от клиентского JS.
2. **Данные — статические JSON в `public/`.** Плюс: просто. Минус: нет схемы, нет валидации, нет версионирования, ручное обновление через загрузку файла в облако — **единая точка отказа и ручной операции**.
3. **Прокси изображений вместо `next/image` с `remotePatterns`.** Само по себе решение рабочее (обход CORS/hotlink‑защиты), но реализация открыта наружу.
4. **Две копии данных.** В корне папки и в `public/` лежат `equipment.json` (99 495 Б и 99 521 Б) и `data_full.json` (164 747 Б и 164 769 Б) — размеры различаются, значит копии уже разошлись. Гарантированно подадут разный контент в разных сборках.
5. **Нет слоя «источник истины».** `sources.json` описывает 13 источников (Nordson ASYMTEK, PVA, Anda, SMT Worldwide, Nutek, Cencorp, ASYS, Saki, ViTrox, Viscom, Rommel), но в данных присутствуют Yamaha, Panasonic, ASMPT, Mycronic, Europlacer, UIC, Heller, BTU, ITW EAE, Rehm, Juki, Koh Young, Universal Instruments — большинство из них в `sources.json` не описаны. **Конфиг и результат работы парсера живут независимо.**

### Целевая архитектура (рекомендация)

```
[Парсер (Python/Node, в репозитории)] ──► [Валидация по JSON‑Schema] ──► [data/*.json в git] 
                                                                          │
[Vercel/CI] ◄── next build (SSG + ISR, revalidate 1 ч) ◄── чтение на сервере
                                                                          │
[Браузер] ◄── SSR/SSG HTML + <Image loader=/api/img> (allowlist хостов, лимиты, кэш)
```

## 4. Доказательная база верификации

### 4.1. Production‑сборка падает — воспроизводимо

```
$ npm run build
▲ Next.js 16.1.6 (Turbopack)
  ✓ Compiled successfully in 4.6s
  Running TypeScript ...
Failed to compile.

./app/page.tsx:111:73
Type error: Property 'model' does not exist on type 'NewsItem | EquipItem'.
  Property 'model' does not exist on type 'NewsItem'.
Next.js build worker exited with code: 1
```

Причина — в `app/page.tsx` состояние модалки типизировано объединением `NewsItem | EquipItem`, а обращения идут к полям обеих моделей сразу (`selectedItem.model ?? selectedItem.title`, `selectedItem.description ?? selectedItem.content`). Всего 6 ошибок TS2339 (строки 111, 116, 119, 120). Dev‑режим это прощает (типы не проверяются), поэтому «всё работает локально» — и это главная ловушка проекта: **артефакт для продакшена не собирается**.

### 4.2. Дополнительный скрытый блокер: сборка требует доступ к Google Fonts

В «чистой» сборке (без правок) падает ещё и на этапе компиляции:

```
[next]/internal/font/google/geist_a71539c9.module.css
next/font: error: Failed to fetch `Geist` from Google Fonts.
```

Для офисного интернета это незаметно, но для **замкнутого промышленного контура** (типичная ситуация на SMT‑производстве с сегментацией сети) или CI без egress — сборка невозможна. Рекомендация: self‑host шрифтов (`next/font/local`) или отказ от внешних шрифтов.

### 4.3. SSRF в `/api/img` — подтверждённый PoC

Локальный «внутренний» сервис на `127.0.0.1:9999` с секретом, затем запрос через прокси приложения:

```
$ curl "…/api/img?url=http%3A%2F%2F127.0.0.1%3A9999%2Fsecret"
INTERNAL-SECRET-12345
HTTP 200 | content-type: text/plain
```

Прокси **выполнил запрос к внутреннему адресу и вернул содержимое наружу**. Сценарии эксплуатации:

| Сценарий | Последствие |
|---|---|
| Скан внутренней сети (`10.0.0.0/8`, `192.168.0.0/16`) | Разведка инфраструктуры завода/офиса |
| Облачные метаданные (`http://169.254.169.254/latest/meta-data/`) | Кража IAM‑ключей (в облачных развёртываниях) |
| Обход ACL по IP | Прокси — «новый источник» для ресурсов, закрытых по IP |
| DoS/ amplification | Нет лимита размера и таймаута → ресурсы сервера исчерпываются |
| Фишинг/XSS | `content-type` отдаётся как есть: `text/html` с вашего origin — см. ниже |

```
$ curl "…/api/img?url=http%3A%2F%2F127.0.0.1%3A9999%2Fevil.html"
<html><body><h1>PHISHING on your origin</h1><script>alert(document.domain)</script>…
HTTP 200 | content-type: text/html
```

То есть через ваш домен можно отдать произвольный HTML/JS — готовый вектор для фишинга и кражи сессий, если появится авторизация.

Что сделано правильно: проверка протокола (`file://` → 400) и обработка отсутствующего параметра (400). Этого недостаточно.

### 4.4. Защитные HTTP‑заголовки — отсутствуют все

## 6. Безопасность — детальный разбор

**P0‑2 (повторю как требование): `/api/img` должен быть переписан:**

```ts
// Требования к исправленной версии
const ALLOWED_HOSTS = new Set([
  'global.yamaha-motor.com','eu.connect.panasonic.com','www.asmpt.com',
  'www.mycronic.com','europlacer.com','www.uic.com','www.sakicorp.com',
  'www.viscom.com','www.jukiamerica.com','www.kohyoung.com',
  'www.heller-industries.com','www.btu.com','www.rehm-group.com','www.vitrox.com'
]);
// 1. Allowlist хостов (не «любой http(s)»)
// 2. Блокировка приватных/loopback/link-local диапазонов (127/8, 10/8, 192.168/16, 169.254/16, ::1, fc00::/7)
// 3. Таймаут (AbortSignal.timeout 5000) и лимит размера (≤ 5 МБ, стриминг + отсечение)
// 4. Content-Type: только image/* (иначе 400/502)
// 5. Rate limit (напр. 60 req/min/IP) + кэш на диске/CDN
// 6. Content-Disposition / X-Content-Type-Options: nosniff
// 7. Логирование отказов (детект попыток сканирования)
```

**Прочее по безопасности:**
- Нет аутентификации/авторизации ни на одном endpoint (сейчас их и нет, но любое развитие — админка, загрузка данных — потребует её сразу).
- Нет CSP → внешние шрифты/скрипты выполняются без ограничений.
- Нет rate limiting на уровне приложения (middleware).
- Секретов в поставке нет — ✅ (но и механизма их управления нет: `.env*` в `.gitignore`, однако `next.config.ts` не читает env — это ок для статики).

**Правовой контур (юридические риски продукта):**
- Парсинг сайтов вендоров: нарушение ToS многих производителей; нет проверки `robots.txt`, нет `Crawl-delay`, нет идентификации краулера.
- Изображения вендоров проксируются с вашего домена — фактически **перераспределение чужого контента**; требуется либо лицензия, либо явная атрибуция + ссылка на источник (ссылка есть — это смягчает, но не решает).
- Нет политики обработки данных / cookie‑баннера — при аудитории EU (вендоры вроде Europlacer/Viscom/Koh Young) это прямой риск по GDPR.
- Нет `Terms of Use` / `Imprint` — обязательно для публичного коммерческого сервиса в юрисдикциях EU/IL.

## 9. Производительность

| Проблема | Факт | Решение |
|---|---|---|
| Два JSON грузятся целиком сразу | 264 КБ (gzip ≈ 47 КБ + 25 КБ) | Серверный рендеринг + пагинация/виртуализация; отдавать только видимую страницу |
| `next dev` отдаёт `Cache-Control: no-store` на HTML | подтверждено заголовком | В продакшене — ISR (`revalidate`) |
| Нет `next/image` | 3 предупреждения линтера | `next/image` + `remotePatterns` **или** свой loader с ресайзом |
| Прокси = лишний хоп на каждую картинку | архитектурно | Кэширование на диске/CDN + `stale-while-revalidate` |
| Апстрим‑запрос с `cache: 'no-store'` | `route.ts` | Разрешено кэшировать; иначе каждый рендер = новый внешний запрос |
| Апстрим без таймаута | `route.ts` | Медленный вендор‑сайт подвешивает рендер карточек |
| Нет `loading.tsx` / Suspense | — | Мгновенный скелетон вместо пустого экрана |
| Тёмная тема в `globals.css` при `bg-gray-50` в коде | конфликт | Решить: либо полноценная тема, либо убрать media‑query |

## 10. SEO, доступность, i18n

- **SEO — критично:** `title: "Create Next App"`, `description: "Generated by create next app"` — это дефолт `create-next-app`, он и попадёт в выдачу и в шаринг‑превью. Нет `sitemap.xml`, `robots.txt`, Open Graph/Twitter‑картинок, JSON‑LD (`NewsArticle`, `Product`), нет канонических URL.
- **Язык:** `<html lang="en">` при полностью русскоязычном интерфейсе и англоязычном контенте. Нужны: `lang` по контенту + `hreflang` при двуязычии.
- **Доступность:** см. §7 — модалка и кликабельные `div`. Также: `alt={item.title}` на картинках карточек (ок) vs `alt="item"` в модалке (плохо); контраст `text-gray-400` на белом (~3:1) ниже WCAG AA для мелкого текста.
- **Мобильная версия:** сетка адаптивна ✅, но модалка `max-height: 90vh` без `overscroll-behavior: contain` — фон скроллится под оверлеем.

## 11. DevOps и эксплуатация

| Проблема | Риск |
|---|---|
| `node_modules/` и `.next/` выложены в общую папку Drive | Раздувание, опасные бинарники из чужих пакетов в доступе, `.next` содержит карты сборки |
| Нет CI/CD (GitHub Actions) | Ручные выкладки, регрессии |
| Нет тестов | Любой рефакторинг — вслепую |
| Нет `.nvmrc` / `engines` | **Next.js 16 требует Node.js ≥ 20.9** (Node 18 не поддерживается; Node 20 с 30.04.2026 — EOL, практическая цель — 22/24). Сборка на чужой машине сломается молча [1][2] |
| Нет Dockerfile / деплой‑инструкции | Невоспроизводимое окружение |
| Нет мониторинга/логов/алертов | Отказы прокси/парсера unnoticed |
| Нет резервного копирования данных | Единственная копия JSON — в облачной папке |
| Нет документации по парсеру | Скрипт «есть у кого-то на машине» — организационный риск |
| Нет версионирования контента | Нельзя откатить кривые данные |

**Минимальный CI‑контур (рекомендация):** GitHub Actions → `npm ci` → `tsc --noEmit` → `eslint` → `vitest run` → `next build` → Lighthouse CI → деплой. Именно это поймало бы P0‑1 автоматически.

## 16. Видение продукта — с позиции SMT & TH‑инженера (30 лет)

Главный актив проекта — не код, а **доменная экспертиза и трафик‑ниша**. Веб‑часть должна быть тонкой и предсказуемой; ценность — в данных и их подаче:

1. **Навигация по процессу, а не по бренду.** Инженер ищет «чем контролировать пайку после рефлоу» или «селективная пайка TH‑компонентов», а не «новости Yamaha». Таксономия по технологическим шагам — ключевая фича.
2. **Спецификации в первую очередь.** Дляplacement‑машин: скорость (cph), точность (±µm), число фидерных позиций, размер платы, диапазон корпусов (01005 … 0,3 mm pitch BGA), Hermes/SECS‑GEM. Для AOI/SPI: разрешение, скорость сканирования, false call rate, IPC‑класс. Это конвертирует «новости» в инструмент выбора оборудования.
3. **Сравнение и «второе мнение».** У вас уже есть `AI_Second_Opinion_for_Koh_Young_3D_AOI` и `Standardizing_AOI_Architecture` — это ровно тот контент, который выделит продукт среди RSS‑агрегаторов: не «что произошло», а «что это значит для линии».
4. **Привязка к документам.** Руководства Ersa VERSAFLOW (palletless, site preparation), материалы по AOI — оцифровать, найти, раздавать через тот же портал. Это удерживающая ценность (retention), которой нет у конкурентов.
5. **Данные о процессе.** Окна пайки, профили рефлоу, параметры селективной пайки, дефектообразование — то, что инженер ищет десятки раз в год и каждый раз заново.
6. **Предсказуемость поставки.** Парсер + CI + ISR = контент обновляется без ручных операций. Сейчас «данные обновляются, если кто‑то запустил скрипт у себя на машине» — это не процесс, это случайность.
